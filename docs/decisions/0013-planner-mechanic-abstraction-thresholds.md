# 0013. DPS 机制抽象阈值：≥2 通用路径，>10 升级注册表

**状态**: Accepted
**决策日期**: 2026-07-30（回填）

## 背景

DPS 机制处理要在「针对单个英雄写死」与「过度抽象（工厂 / 注册表 / 策略链）」之间取折中。需明确何时抽象、何时特化、何时升级为注册表，避免每次新增机制都重判。本决策早于 ADR 约定，现回填。

## 决策

四条阈值（设计语义详见证件 `dps-mechanic-abstraction.md`）：

1. **≥2 抽象**：同一机制被 ≥2 英雄使用 → 必须走通用代码路径（字段分支 / pool 聚合），禁止英雄 id 特化分支。结构性保证（评估路径无英雄 id 特化）。
2. **孤儿特化 + 预警**：机制仅 1 英雄使用 → 可特化，但须确认是否真独一无二。
3. **孤儿→≥2 立刻抽象**：孤儿机制后续变 ≥2 英雄 → 立刻去特化走通用路径。
4. **>10 升级策略注册表**：通用机制总数 >10 → 把字段分支分发重构为策略注册表，不可拖延。

机制 id 三处一致（代码注释 / reference `mechanicIds` / `dps-mechanics.md` 注册表）由 `championReferenceVerification.test.ts` 守护。

## 后果

- 正面：抽象时机有客观线，不靠主观判断；当前 7 机制用字段分支足够。
- 代价：孤儿扫描（阈值 2/3）未自动化，新增 reference 时人工确认机制通用性。
- 风险：机制数增长须及时升级注册表（阈值 4 由测试断言注册表机制数 ≤10 守护）。

## 替代方案

- **逐英雄硬编码**：不选——违背 ≥2 通用路径。
- **一开始就上注册表**：不选——当前 7 机制属过度工程（见 ADR 0008）。
- **无阈值凭主观判断**：不选——每次新增机制都重判，漂移风险高。
