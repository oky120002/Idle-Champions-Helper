# requirements/ —— 需求库

产品层面的**需求库**：将来可能做、但尚未承诺执行的功能。每个文件是一个有边界的需求。

## 回答什么

「将来可能做什么？」——不是系统现状（`specs/`），不是即将执行的变更计划（`plans/`），不是外部事实（`research/`），是**产品意图**：有明确的需求描述和暂缓理由，但没有排期、没有确认启动。

## 与 plans/ 的区别

| | requirements/ | plans/ |
|---|---|---|
| 性质 | 需求意图 | 执行计划 |
| 承诺 | 未承诺，可能永远不做 | 已确认要做 |
| 粒度 | 一个有边界的需求 | 分阶段可执行 checklist |
| 生命周期 | 落地/否决后立即归档 | 用完归档 |

需求被接受并准备执行时，在 `plans/` 新建对应的执行计划，提案保留至实现完成。**一旦实现落地或被否决，必须立即将需求文件移入 `archives/requirements/` 并标记终态，禁止留在 `requirements/` 堆积**（硬约束，见 `governance.md` §7 铁律）。

## 文件格式

每个文件包含：是什么、为何暂缓、关联。

**终态标记**（移入归档时加在文件首）：

- 已落地：`**状态**: 已落地（YYYY-MM，证据：commit / ADR / specs 路径）`
- 已否决：`**状态**: 已否决（理由）`

多子项需求部分落地时，原地更新剩余子项，全部终态后才整体归档；重复或无效提案直接删除，不进归档。

## 命名

`YYYY-MM-<scope>-<slug>.md`（scope = 模块名或 `system`），描述性名称，一个文件一个有边界的需求。

日期取需求首次形成或首次入库的月份：优先使用文档正文明确的需求日期，其次使用 Git 首次引入该文件的日期；两者都不可得时，才使用文件创建日期。后续更新日期不改变文件名。
