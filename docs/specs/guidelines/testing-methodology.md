# 测试方法论

项目级硬约束。测试必须证明可观察的业务行为、边界契约和关键不变量；测试数量不是覆盖质量的替代品。

## 1. 测试金字塔与层级选择

- 选择能够证明行为的最低成本层级：

| 层级 | 必须证明的内容 |
|---|---|
| 单元 | 纯函数、规则、公式和边界分类 |
| 集成 | 模块接缝、真实产物流转、持久化或网络适配边界 |
| 组件 | 页面局部交互、可访问性和组件可观察状态 |
| E2E | 用户可见的完整流程、路由、浏览器和部署边界 |

- 缺陷修复至少补一个最低层级回归；缺陷跨模块时，另补接缝契约测试。不得只补 E2E 证明内部计算正确。
- E2E 只覆盖高价值用户路径；不得用大规模 E2E 代替快速、隔离的单元和集成测试。

## 2. 行为契约优先

- 测试优先断言输出、状态、异常、warning、持久化结果和不变量；只有调用次数、内部结构本身是公开契约时才断言实现细节。
- 测试名称描述业务行为和输入条件，不描述私有函数步骤；失败信息必须能定位到样本、字段和接缝。
- 正例、缺省、非法输入和恢复路径分开命名；不能用一个宽泛的“不会崩溃”覆盖不同语义。

## 3. 生产形状、真实产物与 schema

- fixture builder 的默认值必须是生产合法值；异常 fixture 必须显式标注损坏字段和预期行为，不能让非法值混入通用默认夹具。
- 数据归一化 → build → runtime → 展示的链路必须有真实产物端到端守护；合成 fixture 只补局部规则和组合，不替代真实接线。
- 真实产物守护必须断言结构、语义和聚合结果（pool/total/carryDps），不能只断言中间信号存在或流程没有抛错。聚合整体难对照时，断言其组成（addPercent 各来源、各 pool 分量）。
- 跨边界一致性无法合并为单一来源时，必须配 keys 同步守护测试；任一侧漂移都要失败。
- zod 守外来数据的运行时形状，TS 守内部代码的编译期类型；二者不能互相替代。外部 collection 只钉消费方核心字段并 passthrough，项目自著数据使用 strict schema。
- schema 放 `scripts/data/*-schema.ts`，co-located 测试覆盖合法样本、类型、枚举、必填和 nullable 变异；真实产物经 `pnpm run data:validate-schema` 校验，失败必须非零退出。

## 4. 隔离与确定性

- 每个测试独立准备和清理外部状态（IndexedDB、文件、网络 mock、计时器、worker）；测试顺序、并发和重复运行不得改变结果。
- 禁止未设种子的随机数、真实时间和真实网络进入可重复测试；必须固定输入或显式注入依赖。
- 纯计算入口应保持输入不可变；相同输入重复调用必须得到相同的结构化结果。

## 5. 决策表与不变量

- 多个条件会交互时用决策表或参数化测试覆盖等价类、边界和组合，不用若干孤立 happy path 代替。
- 计算和搜索链至少为关键规则定义可执行不变量，例如：确定性、输入不可变性、聚合交换律、单调性、合法性、因子之积复现目标值。
- breakdown 声称“因子之积 = 目标值”时，必须测试多个因子同时非默认值；同一 add pool 的多个来源必须验证加法合并，而非各自独立相乘。
- 数值边界至少覆盖零、正数、负数、非有限值、缺省值和业务哨兵；显式零与未传入必须分别测试。

## 6. 变异证伪

- 每条关键规则至少指定一个最小变异点：删除校验、反转比较、替换常量、漏乘因子、覆盖而非累加、跳过一条来源。
- 变异后对应测试必须失败；手动变异和自动 mutation runner 均可，验证时必须确认变异确实生效，禁止依据未生效的变异得出“已覆盖”结论。
- 变异验证优先用于 planner 公式、数据聚合、排序、合法性和跨模块契约；不为纯展示文案引入重型 mutation 流程。

## 7. 集成边界与异常输入

- 每条模块接缝先判定输入属于哪一类：
  - **契约损坏**：必填字段缺失、类型错误、非法枚举、悬空引用、`NaN` / `Infinity`、违反值域的负数或非正数。内部契约和计算核心必须 `throw` / `reject`，禁止改成 `0`、`1`、空集合、跳过或只写 warning。
  - **业务缺省**：明确允许缺失且有业务定义的默认值（如乘法单位元、官方哨兵值、未拥有英雄的估算等级）。只对“未传入”回退；显式非法值不能伪装成缺省。
  - **可恢复外部故障**：缓存损坏、可选资源缺失、官方镜像失败等，只有在产品定义允许继续时才能回退；必须校验替代数据，并在结果、状态或 warning 中保留可观察证据。
  - **未建模业务**：若产品明确选择保守不计入目标值，测试必须断言 warning / blocker 和“不计入”，不能只断言不崩溃。
- 异常用例至少覆盖缺失、错误类型、`NaN`、`Infinity`、负数 / 非正数、非法枚举和悬空引用；预期 fail-fast 时使用 `toThrow` / `rejects.toThrow`，并断言错误指向具体字段或接缝。
- 禁止用空 `catch` 或默认值吞掉未分类异常。批量 smoke 若必须继续收集其他样本，需保留样本 id、原始错误和失败数量，最终以非零断言失败。
- 每个回退都必须在测试名称、断言和对应 spec 中说明触发条件、业务理由及“不会发生什么”；未能说明理由的回退按契约损坏处理。

## 8. 跨边界契约与断言强度

- producer → consumer 的测试同时验证结构契约和语义契约：字段类型/枚举/引用完整，且最终计算、聚合或页面状态正确。
- 对计算链使用对抗性变异验证断言强度：篡改一个上游字段后，测试应明确证明抛错、可观察降级或不变量破坏被捕获。
- 契约测试补充而非取代单元测试；单元证明局部规则，集成证明接线，E2E 证明用户流程。
- 测试必须有能失败的断言，且失败时返回非零；只打印统计、只检查对象存在、只使用 `toBeTruthy` 或只断言“不抛错”不能作为关键行为的唯一门禁。
- 断言优先使用稳定的行为和不变量；对真实数据变化敏感的精确基线必须有显式更新命令和审查入口。
- 新方法论规则落地后，必须在对应测试入口运行并纳入 `test:regression` 或明确的专项 gate，不能成为只存在于文档中的建议。
- 变更异常处理、默认值或回退语义时，必须同步更新调用方、负例测试、模块 spec 和审计记录；不能只改测试让旧的静默行为继续存在。
